## 2. 현재 상태 분석

### 2.1 인증

인증 관련 코드·환경변수·의존성이 **전무**하다. 전 경로가 공개 상태다.

### 2.2 match-maker (`src/app/tools/match-maker/page.tsx`, 1344줄)

전량 `"use client"` 클라이언트 컴포넌트이며, 상태는 **브라우저 `localStorage` 단독**으로 관리된다.

```
STORAGE_KEY = "tennis-king:match-maker:v1"

PersistedState {
  guests: Player[]              // 게스트 명단
  selectedIds: string[]         // 참가 선택 인원
  gamesPerPlayer: number        // 1인당 게임 수
  bracket: BracketResult | null // 생성된 대진표
  scores: Record<number, MatchScore>  // 경기별 점수
}
```

핵심 제약: **이 상태는 브라우저 하나에 갇혀 있다.** A가 점수를 입력해도 B의 화면에는 아무 일도 일어나지 않는다. R3를 만족하려면 이 상태를 서버로 올려야 하며, 이는 이 프로젝트에 **처음으로 서버 사이드 영속 상태를 도입**하는 변경이다.

대진표 생성 로직(`src/lib/match-maker.ts`)은 순수 함수라 서버/클라이언트 어디서든 재사용 가능하다. 이 파일은 수정 대상이 아니다.

### 2.3 Next.js 16 관련 확인 사항

`node_modules/next/dist/docs/` 확인 결과:

- **`middleware.ts` → `proxy.ts` 로 이름이 바뀌었다** (Next.js 16). 기능은 동일. `src/app`을 쓰므로 파일 위치는 **`src/proxy.ts`**.
- **Proxy는 Node.js 런타임에서 동작한다.** `runtime` 설정은 불가하며 지정 시 에러. → **`node:crypto`를 그대로 쓸 수 있어 `jose` 등 추가 의존성이 필요 없다.**
- 공식 문서 경고: *"Proxy는 최초 필터일 뿐 유일한 방어선이 되어서는 안 된다. 대부분의 보안 검사는 데이터 소스에 최대한 가까운 곳에서 수행하라."* → **Route Handler에서도 세션을 반드시 재검증한다.**

## 4. Feature A — 가입코드 접근 제어

### 4.1 동작 흐름

```
방문자 → 아무 경로 요청
          │
     src/proxy.ts : 세션 쿠키 검증
          │
    ┌─────┴─────┐
  없음/무효      유효
    │             │
 /gate 리다이렉트  요청 통과
 (?next=원래경로)
    │
 코드 입력 폼
    │
 Server Action: 코드 대조 (timing-safe)
    │
  ┌─┴─┐
 불일치  일치
  │      │
 에러   서명 쿠키 발급 → 원래 경로로 redirect
 표시
```

### 4.2 신규/변경 파일

| 파일 | 종류 | 내용 |
|---|---|---|
| `src/lib/auth/session.ts` | 신규 | HMAC-SHA256 토큰 발급/검증, 쿠키 read/write/delete |
| `src/app/gate/page.tsx` | 신규 | 코드 입력 화면 (사이드바 없는 독립 레이아웃) |
| `src/app/gate/layout.tsx` | 신규 | 게이트 전용 레이아웃 (Sidebar 미노출) |
| `src/app/gate/actions.ts` | 신규 | Server Action — 코드 검증 → 쿠키 발급 → redirect |
| `src/proxy.ts` | 신규 | 세션 없으면 `/gate` 리다이렉트 |
| `.env.local` | 신규 (git 미추적) | `SESSION_SECRET`, `CLUB_ACCESS_CODE` |
| `.env.example` | 신규 | 키 이름만 담은 템플릿 (커밋 대상) |
| `src/components/Sidebar.tsx` | 변경 | 하단에 "나가기" 버튼 추가 (쿠키 삭제) |

### 4.3 세션 토큰 설계

추가 의존성 없이 `node:crypto`만 사용한다.

```
토큰 = base64url(payload) + "." + base64url(HMAC-SHA256(payload, SESSION_SECRET))
payload = { exp: <만료 epoch ms> }
```

- 담을 정보가 만료시각뿐이다 — 익명 접근이므로 사용자 식별자가 없다.
- 쿠키 옵션: `httpOnly`, `secure`(prod), `sameSite: "lax"`, `path: "/"`, 만료 **30일**
- 코드 비교는 `crypto.timingSafeEqual` 로 수행 (타이밍 공격 차단)
- 서명 검증 실패·만료 시 쿠키 삭제 후 `/gate` 리다이렉트

### 4.4 proxy matcher

```ts
export const config = {
  matcher: ["/((?!gate|api/health|_next/static|_next/image|favicon.ico|.*\\.(?:png|jpg|svg|ico)$).*)"],
};
```

- `/gate` 자체와 정적 자산은 제외 (제외하지 않으면 무한 리다이렉트)
- **`/api/*`는 matcher에 포함한다** — 데이터가 나가는 경로이므로 반드시 막아야 한다

### 4.5 이중 방어

`src/app/api/**` Route Handler는 진입부에서 `verifySession()`을 직접 호출하고, 실패 시 `401`을 반환한다. proxy만 신뢰하지 않는다 (Next.js 공식 문서 권고).

### 4.6 운영 시나리오

- **코드 배포**: 클럽 단톡방 공지
- **코드 변경**: `CLUB_ACCESS_CODE` 환경변수 교체 → 재배포. 기존 세션 쿠키는 서명이 유효하므로 30일간 유지된다. 즉시 전원 로그아웃이 필요하면 `SESSION_SECRET`도 함께 교체한다.
- **유출 대응**: 위 두 값 교체 + 새 코드 재공지

### 4.7 보안 한계 (명시)

- 코드를 아는 사람은 누구나 통과한다. 회원 개개인 구분·특정인 차단은 **불가능**하다.
- 코드가 외부로 퍼지면 재발급 외에 대응 수단이 없다.
- 사이트 콘텐츠 민감도(공지·회원 이름·NTRP)를 고려하면 현 단계에서 수용 가능한 수준으로 판단한다.

## 5. Feature B — 대진표 실시간 공유

### 5.1 저장소 선택 (D2)

localStorage를 서버 상태로 옮기는 것이 핵심이며, 저장 매체 선택이 실현 가능성을 좌우한다.

| 후보 | 평가 |
|---|---|
| **Upstash Redis** (Vercel Marketplace) | **권장.** 무료 티어(일 10,000 커맨드)로 충분. REST 기반이라 서버리스 친화적. 단일 키 JSON 저장이면 스키마 작업 불필요 |
| Vercel Postgres / Supabase | 동작하나 스키마·마이그레이션 부담이 이 규모에 과함 |
| 서버 프로세스 메모리 | **Vercel에서는 불가** — 요청마다 다른 인스턴스로 분산되어 상태가 유실된다. **자체 단일 Node 서버 배포라면 가능**하며, 이 경우 인프라 추가 없이 구현 가능 (D1에 종속) |
| 파일시스템 | **불가** — Vercel 파일시스템은 읽기 전용이며 휘발성 |

> D1이 "자체 Node 서버"로 확정되면 D2는 서버 메모리로 단순화할 수 있다. 단 서버 재시작 시 진행 중인 게임 상태가 사라진다는 점은 감수해야 한다.

### 5.2 데이터 모델

"현재 진행 중인 게임" 단 하나만 유지한다. 과거 이력 보관은 이번 범위에 포함하지 않는다.

```ts
// src/lib/match-session.ts (신규)
interface SharedMatchSession {
  version: number;        // 낙관적 락 — 수정 시마다 +1
  updatedAt: string;      // ISO 8601
  guests: Player[];
  selectedIds: string[];
  gamesPerPlayer: number;
  bracket: BracketResult | null;
  scores: Record<number, MatchScore>;
}
```

기존 `PersistedState`에 `version` / `updatedAt` 두 필드만 추가한 형태다.

### 5.3 API 설계 (Route Handlers)

| 메서드 | 경로 | 동작 |
|---|---|---|
| `GET` | `/api/match-session` | 현재 상태 전체 반환. 없으면 초기값 |
| `PUT` | `/api/match-session` | `{ version, patch }` 수신 → version 대조 → 저장 후 `version+1` 반환. 불일치 시 **409 + 서버 최신 상태** |
| `DELETE` | `/api/match-session` | 초기화 (🗑 버튼) |

- 모든 핸들러 진입부에서 세션 쿠키 재검증 (§4.5)
- 대진표 생성은 **서버에서 수행**한다. 클라이언트가 각자 생성하면 난수 때문에 사람마다 다른 대진표가 나온다. `generateBracket()`은 순수 함수라 서버 이관에 문제가 없다.
- 게스트 ID도 서버에서 발급한다 (현재 `Date.now()` 기반 클라이언트 생성 → 동시 추가 시 충돌 여지 제거)

### 5.4 동시 편집 처리 (D3 — 전원 수정 가능 확정)

**전원 수정 가능 + 낙관적 락**

1. 클라이언트는 보유 중인 `version`을 함께 전송
2. 서버 `version`과 일치 → 반영, 불일치 → `409` + 서버 최신 상태 반환
3. 클라이언트는 409 수신 시 서버 상태로 갱신하고 *"다른 분이 먼저 수정했습니다"* 토스트 표시

점수 ±1 정도의 단순 조작에서 이 정도면 실사용에 충분하다.

**원자성 확보**: `GET` 후 `SET` 하는 2단계 방식은 그 사이에 다른 요청이 끼어들 수 있어 락이 새어나간다. Upstash REST의 `EVAL`로 **Lua 스크립트 안에서 버전 비교와 저장을 한 번에** 수행한다. 정확성이 보장되고, 커맨드도 2건이 아닌 1건으로 줄어든다.

**의존성**: `@upstash/redis` SDK를 쓰지 않고 **`fetch` 기반 얇은 어댑터**로 처리한다. 필요한 연산이 `GET` / `EVAL` 둘뿐이고 값도 JSON 문자열 하나여서 SDK의 이점이 크지 않다. 지금까지 유지해 온 "추가 의존성 0개" 상태를 이어간다.

### 5.5 실시간 반영 방식 (확정)

**10초 주기 폴링.** SSE/WebSocket은 Vercel 함수 실행시간·비용과 재연결 처리 복잡도 때문에 이번 범위에서 제외한다.

| 트리거 | 동작 |
|---|---|
| 마운트 (진입·**새로고침**) | **즉시 1회 조회** 후 10초 주기 시작 |
| `visibilitychange` → visible | **즉시 1회 조회** 후 10초 주기 재개 |
| `visibilitychange` → hidden | 폴링 중단 (요청 0건) |
| 쓰기(`PUT`/`DELETE`) 성공 | 응답 본문에 최신 상태가 포함되므로 별도 조회 없음. 폴링 타이머만 리셋 |
| 5분간 무조작 | 폴링 일시중지 + UI 표시. 복귀·조작 시 재개 |

설계 원칙:

- **화면 비활성 시 완전 중단**이 사용량 절감의 지배적 요인이다. 모임 중 대부분의 폰은 잠겨 있다.
- **"복귀 즉시 조회"는 UX상 필수**다. 경기 후 폰을 꺼내는 순간이 곧 결과 확인 시점이라, 여기서 10초를 대기시키면 안 된다.
- **폴링 1회 = Redis 커맨드 1건.** 버전 확인과 본문 조회를 분리하지 않고 단일 키를 통째로 읽는다.

### 5.6 무료 티어 사용량 검토

Upstash Redis 무료 티어: **월 50만 커맨드 / 256 MB / 10 GB 대역폭** (2026-08 확인. 2025-03 이후 일일 1만 건 제한 폐지).

**실제 사용 계획: 월 4회 모임 × 회당 4시간.** 10초 폴링 = 활성 사용자 1인당 분당 6건.

| 시나리오 | 가정 | 모임 1회 | 월 4회 | 한도 대비 |
|---|---|---|---|---|
| 현실적 | 10명, 1인당 실제 화면 확인 20분 | 1,300 | 5,200 | 1% |
| 보수적 | 12명, 1인당 1시간 | 4,500 | 18,000 | 3.6% |
| 최악 | 14명 전원이 4시간 내내 화면 켜둠 | 20,500 | **82,000** | **16%** |

**최악 시나리오에서도 한도까지 6배 여유**가 있다. 대역폭은 최악 기준 400 MB 내외(한도 10 GB), 저장 용량은 키 1개 수 KB로 무관하다.

> Vercel 함수 호출 수(폴링 1회 = Route Handler 1회)도 최악 8만 건 수준이라 무료 범위 안이다. 그럼에도 첫 달은 Upstash·Vercel 양쪽 대시보드에서 실사용량을 확인한다. 이상 징후 시 폴링 주기를 20초로 늦추면 절반이 된다.

- 충돌·오류 발생 시 토스트 — **조용히 무시하지 않는다**

UX 결정 필요 항목:
- **생성 애니메이션(`GenerationOverlay`, 3.35초)**: 생성 버튼을 누른 사람에게만 보여줄지, 전원에게 보여줄지. 기본안은 **누른 사람에게만** — 폴링 구조에서 전원 동시 재생을 맞추기 어렵고, 다른 사람은 완성된 대진표를 3초 내에 받는다.
- **최종 순위 모달(`FinalRankingModal`)**: 마찬가지로 각자 버튼을 눌러 확인하는 방식 유지.

| **2** | 공유 상태 백엔드 | D3 확정 | ✅ **코드 완료** — `match-session.ts`, `redis.ts`, `match-session-store.ts`, `api/match-session/route.ts` |

### Phase 2~3 구현 메모

- **API**: `GET`(조회) / `PUT`(편집 저장) / `POST`(대진표 생성) / `DELETE`(초기화). 모든 핸들러가 `hasValidSession()` 으로 세션을 재검증한다.
- **proxy 예외 처리**: `/api/*` 는 리다이렉트 대신 **401 JSON** 을 반환한다. fetch 클라이언트가 로그인 페이지 HTML 을 JSON 으로 파싱하려다 실패하는 것을 막는다.
- **게스트 ID**: 계획 초안의 "서버 발급" 대신 클라이언트 `crypto.randomUUID()` 를 쓴다. 동시 추가 충돌은 동일하게 해소되면서 왕복 1회를 줄인다.
- **폴링 중 편집 보호**: 저장되지 않은 로컬 편집이 있으면 폴링 결과를 적용하지 않는다. 입력 중인 값이 덮어써지는 것을 막는다.
- **쓰기 직렬화**: 400ms 디바운스 + 동시 1건만 전송. 실패 시 편집을 큐에 유지하고 5초 후 재시도한다 (조용한 유실 없음).
- **초기화 시 큐 폐기**: 대기 중인 쓰기를 취소한다. 그러지 않으면 삭제한 대진표가 되살아난다.
- **생성 애니메이션**: 오버레이 재생과 서버 요청을 병렬로 돌려 대기시간을 감춘다 (누른 사람만 오버레이를 본다).

Phase 1과 Phase 2는 서로 독립적이다. Phase 1을 먼저 배포해 사이트를 잠근 뒤 Phase 2~3을 진행하는 순서를 권장한다.

### Phase 1 배포 전 필수 작업

Vercel 프로젝트 환경변수에 아래 두 값을 등록해야 한다 (Production/Preview 모두). **등록하지 않으면 사이트가 500 에러로 열리지 않는다** — 시크릿 누락 시 통과시키지 않고 명시적으로 실패하도록 설계했다.

| 변수 | 값 |
|---|---|
| `SESSION_SECRET` | `openssl rand -base64 32` 로 생성한 값 (로컬과 달라도 무방) |
| `CLUB_ACCESS_CODE` | 회원에게 공유할 가입코드 |

### 검증 중 발견·수정한 결함

| 결함 | 증상 | 조치 |
|---|---|---|
| Lua `cjson.decode` 오판 | 손상된 저장값에서 `attempt to index a non-table object(nil)` 로 스크립트 실패. Redis 의 `cjson.decode` 는 잘못된 입력에 예외를 던지지 않고 `nil` 을 반환해 `pcall` 이 성공으로 판정됨 | 인덱싱 전에 `type(decoded) == 'table'` 검사 추가 |
| 연속 입력 유실 | 6명을 연속 클릭했는데 마지막 1명만 저장. 핸들러가 렌더된 state 를 읽어, 리렌더 전 연속 입력이 모두 같은 낡은 값을 기준으로 계산됨 (점수 연타에도 동일 영향) | 훅에 **함수형 업데이트** 추가 — 이전 값에 의존하는 변경은 항상 ref 의 최신 상태에서 계산 |
| API 401 대신 307 | 세션 만료 시 폴링 fetch 가 `/gate` HTML 을 받아 JSON 파싱 실패 → 원인 불명의 "연결 끊김" | proxy 에서 `/api/*` 는 리다이렉트 대신 401 JSON 반환 |
